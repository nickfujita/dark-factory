1. **Critical — §1, §5, D22: Codex invocation is not implementable as written.** Claude’s `disable-model-invocation` frontmatter does not establish equivalent behavior in Codex. Codex skills are normally invoked as `$df`; `/df` requires a separate custom-prompt or command implementation. A description saying “explicit only” is policy, not enforcement. **Fix:** Choose a Codex-native entry point, document its installation, and add clean-session tests proving that ordinary prompts cannot activate it while explicit invocation can.

2. **High — §1, §2, Appendix: The SessionStart behavior contradicts itself and lacks a Codex implementation.** §1 says the hook “does not activate the mode,” while the `poteto-mode` disposition says “SessionStart hook loads it.” Claude hook semantics cannot simply be assumed on Codex. **Fix:** Define “load,” “remind,” and “activate” separately; specify harness-specific mechanisms; and test fresh session, resume, and post-compaction behavior in both harnesses.

3. **High — §1, D17, D22: “df owns all development work” conflicts with explicit opt-in.** Development work performed without `/df` necessarily proceeds outside df, so df cannot own all development work while entry remains optional. **Fix:** Decide whether the claim is “df owns all explicitly routed work,” or whether uninvoked development receives a reminder/refusal. Record that decision separately.

4. **High — §2, §5, Appendix: The one-owner rule is already violated.** `how` and `why` can self-trigger for investigation while `df` owns investigation; `interrogate` overlaps `df-code-review`; `swarm` overlaps QA routing; `unslop`, `technical-writing`, and `df-open-pr` all own prose quality; worktree cleanup is both folded and retained. **Fix:** Produce an exhaustive function map identifying one public entry point per function. Mark supporting material as non-triggering libraries or references.

5. **High — §2, §5, Appendix: The proposed skill/file structure is internally inconsistent.** The owner table names `df-pause` and `df-pickup`, but the appendix retains `playbooks/pause-safely.md` and `playbooks/session-pickup.md`. `df-plan`, `df-open-pr`, and `df-eval` appear both as skills and as playbook dispositions despite the rule that playbooks are not separately triggered skills. **Fix:** Add a canonical target-tree manifest listing every skill, playbook, agent, script, entry point, and trigger status.

6. **High — §4–§5: “One policy core” has no synchronization mechanism.** Manually rewritten Claude and Codex trees will drift, especially where frontmatter, invocation, tools, permissions, and agent definitions differ. A trigger-text audit will not detect semantic divergence. **Fix:** Keep one canonical methodology source, generate thin harness adapters, and add a parity check over shared sections plus harness-specific behavioral tests.

7. **High — §1, §3, §8: The plan still contains an unacknowledged coexistence phase.** Superpowers remains active until df passes evals, so both methodologies coexist during porting and validation. Its mandatory trigger behavior can contaminate those evals and reproduce the routing conflict the plan claims disappears. **Fix:** Validate df in isolated Claude/Codex configuration homes, or disable superpowers before testing with a pinned rollback path. Add this cutover choice to the ledger.

8. **High — §6: The Claude model policy contradicts its throttle premise.** The text says top-tier pins must never silently defeat a downgraded root, yet implementation, synthesis, and design roles explicitly select Opus. A pinned `Opus high` role is an actual selection, not merely a “floor.” **Fix:** Make those roles inherit by default, or define explicit quota/reserve conditions under which a pin may override the session throttle.

9. **High — §6: `model-policy.md` is not an enforceable configuration format.** Free-form role names and values such as `opus + inherit` cannot be reliably parsed. `profiles/*.env` is also not a native Codex profile mechanism; Codex profiles live in its CLI configuration and require explicit selection. **Fix:** Use a versioned TOML/YAML schema, build one resolver per harness, validate model and agent identifiers at preflight, and record the resolved value and source in every run ledger.

10. **High — §6: Codex custom-agent mechanics are underspecified.** The document alternates between hyphenated and underscored agent identifiers. It also omits the constraint that a full-history fork inherits the parent model and effort and cannot simultaneously select a differently pinned custom role. **Fix:** Ratify canonical registration keys and require bounded/no-history briefs when selecting custom agents. Add spawn smoke tests and an explicit automatic condition for the Luna-to-Terra fallback.

11. **High — §5: “Readonly becomes sandbox flags plus instruction” is false for native subagents as a general substitution.** Local native subagents share the workspace, and a per-child sandbox cannot be assumed. An instruction is not a write barrier. **Fix:** Run independent reviewers in an actually read-only process or immutable worktree/snapshot. Serialize writers sharing a worktree, with explicit file ownership embedded in `df-implement`.

12. **High — §5–§6: `codex exec` is incorrectly treated as interchangeable with a native subagent.** A fresh `codex exec` does not inherit the parent conversation, active df mode, todo state, or adjudication context. The document specifies neither working directory nor input/output transport. **Fix:** Define a reviewed wrapper that supplies the exact brief, artifact digest, cwd, profile, sandbox, approval mode, deadline, output schema, and exit-status mapping.

13. **High — §6: Cross-model execution is asymmetric and operationally unsafe.** “Fresh `codex exec`” is headless, while “Claude tmux” is an interactive-session technique with no equivalent structured completion contract. Running a nested CLI in the Matrix bridge pane can also break session routing. **Fix:** Give both directions supervised, noninteractive adapters with dedicated processes or detached sessions, structured output, deadlines, cancellation, and a rule forbidding use of the bridge pane.

14. **High — §5, Appendix: `Monitor`, “until-loops,” and “the loop skill” are not defined portable primitives.** Neither harness can be assumed to provide PSTACK’s wake semantics, and a polling agent can become another runaway session. **Fix:** Implement an external bounded supervisor with maximum polls, maximum elapsed time, progress predicates, and a terminal stalled state. Do not leave wake behavior as prose substitution.

15. **High — §5: A gates-file entry is not an equivalent to asking the operator.** A headless child can write a gate and then continue, or the parent can miss it. **Fix:** Gate creation must be atomic, terminate the child as `blocked-awaiting-human`, and require a uniquely identified answer event before any resume.

16. **High — §2: Cross-repository project assets may be inaccessible on Codex.** A Spellguard manifest pointing at sibling-repo Spellbook depends on cwd, sandbox roots, and machine-specific paths. “Profiles” do not automatically grant that access. **Fix:** Define portable path resolution and an explicit read-only additional-root mechanism, or export a pinned catalog snapshot into the target repo.

17. **High — §2: `.dark-factory/project.yaml` creates an unaddressed trust boundary.** It names files and executable test commands, potentially from an untrusted branch. It could direct an agent toward sensitive paths or arbitrary shell commands. **Fix:** Version and validate the schema; canonicalize and allowlist paths; reject unsafe symlinks; replace raw command strings with approved command IDs; and require explicit trust for project-local skills.

18. **Critical — §2, §6–§7: The cap-enforcement state store is not specified strongly enough to prevent another runaway.** “Lock semantics kept” does not establish where state lives across worktrees and harnesses, how stale locks work, or how concurrent agents reserve dispatches. Checking a cap after spawning is too late. **Fix:** Specify a single authoritative store with schema versioning, atomic pre-dispatch reservation, leases, idempotency keys, stale-owner recovery, and terminal states. Test concurrent dispatch and resume races.

19. **High — “What survives of the re-review loop”: The artifact-version rules conflict.** A changed SHA supposedly earns one fresh pass, yet remediation receives delta verification, flag-flip remediation may need another check, and the operator can request a second opinion. PRDs and dirty worktrees may not have a meaningful head SHA at all. **Fix:** Key reviews by content digest and define a matrix of allowed pass types and counters for discovery, delta confirmation, integrated review, and operator second opinion.

20. **High — §2, D13, D21: Review termination and gating remain ambiguous.** The five-round breaker is still a multi-round loop, but round accounting, adjudicator cost, and terminal outcomes are absent. “Gates unchanged” does not say whether a second opinion’s new Critical or High finding blocks delivery. **Fix:** Define a finite state machine with numeric per-task caps, adjudication included inside the budget, and explicit ship/block/defer outcomes for every pass type.

21. **High — §2, §4: The frozen-tree and integrated-review mechanics are missing.** Earlier PRs merge independently, main can acquire unrelated changes, and the final flag PR is not itself the assembled feature chain. “Once per chain” also conflicts with remediation after that pass. **Fix:** Record the feature’s start base and exact merge commits, review an immutable commit, invalidate verdicts on patch change, and permit one bounded delta confirmation after integrated-review remediation.

22. **High — §4: A config boolean is not a sufficient feature-flag convention.** It does not cover schema changes, protocols, credential behavior, default state, stale branches, or flag cleanup. **Fix:** Define default-off behavior, compatibility rules, tests in both states, cleanup ownership/date, rollback behavior, and criteria requiring a branch chain or single atomic PR instead of a flag.

23. **Medium — §2: The Quick-lane TDD escape conflicts with bug-fix discipline.** “Prefer no new test” can allow a reproduced defect to ship without a regression guard. **Fix:** Make executable regression coverage mandatory for reproducible bugs and trust-boundary changes unless an explicit, recorded exception explains why no stable test is possible.

24. **High — §8: The execution order is impossible as stated.** The baseline run starts “as soon as the ports land,” but run-state schemas, project hooks, feature maps, and `verify-spellguard` are scheduled later even though the baseline depends on them. **Fix:** Replace table order with a dependency graph: isolated adapters and state store, vertical-slice skills, project manifest/catalog, verifier, then baseline run, followed by fleet rollout.

25. **High — §8: The “about a day” port estimate lacks an acceptance-based inventory.** The plan covers dozens of skills and playbooks, two harness adapters, scripts, trigger audits, cross-model wrappers, and scenario tests. Semantic porting and cross-harness validation dominate the work, not Markdown transcription. **Fix:** Estimate by target artifact and acceptance test, and first ship one complete route—such as bug fix—before extrapolating to the catalog.

26. **High — §8: There is no canary or rollback plan for fleet-wide behavioral changes.** The work removes provisioned global instructions and uninstalls the current workflow plugin across both harnesses. Reinstallation “takes minutes” is not a tested rollback. **Fix:** Pin the exact old plugin and instruction revisions, canary one VM, run clean-session and resume smoke tests, define rollback tripwires, then roll out VM by VM.

27. **High — §6, §9: Hard-ceiling protection lacks numeric and transitive enforcement.** Wall time and top-level dispatch count do not bound nested subagents, and exhaustion is detected only after a CLI call fails. `D1–D10: CC defaults` leaves the critical numbers outside the ratification package. **Fix:** Inline the actual caps, count nested dispatches against the parent budget, reserve capacity before spawning, preserve a cross-model review quota, and define exact usage-limit versus auth/network/error classification.

28. **High — §9: The ledger omits decisions essential to implementation.** Missing decisions include the Codex entry mechanism, canonical dual-harness source, transition isolation, native-subagent versus `codex exec` selection, shared-worktree policy, state-store location, project-manifest trust policy, second-opinion gating, feature-flag lifecycle, cross-model launcher contract, and canary/rollback strategy. **Fix:** Add these as explicit D23+ decisions before ratification.

29. **High — §1–§2, Appendix: Non-feature router branches are names, not executable contracts.** Investigation, bug, perf, refactor, prototype, autonomous-run, babysit, and fallback `figure-it-out` lack a complete routing matrix covering lane, allowed writes, required artifacts, review gates, finish predicates, and escalation. **Fix:** Define that matrix and make the router machine-check it.

30. **High — §4, §8: Live verification lacks environment and credential controls.** The plan does not identify the deployed revision, service prerequisites, test-data isolation, reset strategy, secret source, or evidence needed to prove a run exercised the intended build. This is material for a credential product. **Fix:** Put verified prerequisites, health checks, revision attestation, credential provenance, data cleanup, and blocked-environment handling into the project manifest contract and QA ledger.

31. **Medium — §7: The eval design relies on unstable and sensitive transcript internals.** Transcript locations and formats differ between harnesses and may change; transcripts can contain credentials or personal material. Pass thresholds, holdouts, and nondeterminism handling are also absent. **Fix:** Introduce versioned transcript adapters, redact before storage, define retention, use fixed fixtures and holdout scenarios, and specify objective pass/fail thresholds.

32. **Medium — §3, §5: Porting provenance is incomplete.** Superpowers is identified as MIT reference material, but PSTACK’s license, exact source revision, and per-file provenance are not recorded. Quarterly manual cherry-picking also becomes irreproducible without a baseline. **Fix:** Add a vendor manifest containing repository URL, license, commit hash, source-file mapping, local modifications, and attribution requirements.

**Overall verdict:** Not ready for ratification or port day. The conceptual boundary is stated, but the Codex invocation model, cross-model process contract, cap-enforcement store, dual-harness synchronization, and cutover sequence are unresolved implementation dependencies.
