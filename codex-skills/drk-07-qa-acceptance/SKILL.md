# QA Acceptance Execution

Execute a QA acceptance runbook against a running application using
agent-browser. Runs each test case, captures results, and produces a
structured report.

## Prerequisites

- A QA runbook file (generated by drk-03-qa-runbook-gen or manually authored)
- The target application must be running and accessible
- agent-browser must be available (`agent-browser --version`)
- For rerun mode: a previous immutable results report and latest pointer for
  the same runbook

## Workflow

### Step 1: Parse the Runbook

Read the QA runbook file. Extract:
- YAML frontmatter (`base_url`, `timeout`, optionally `auth`)
- Preconditions section (setup requirements before testing)
- All test cases with their steps, assertions, and priorities
- Sort test cases by priority: P0 first, then P1, then P2

**Validate the runbook** after parsing:
1. At least one test case was extracted
2. Every test case has at least one assertion
3. Every test case has a priority tag
4. Test case IDs are unique

If validation fails, stop and report the specific parsing errors rather
than executing an invalid runbook.

Resolve `base_url`:
- Default to frontmatter `base_url`
- If missing/blank, ask the user for the base URL before execution
- User-provided override takes precedence over runbook frontmatter
- **URL normalization**: strip trailing slash from `base_url`
- **Safety guard**: only run against local/dev/test hosts (`localhost`,
  `127.0.0.1`, `::1`, `.local`, `.test`, `.dev`). If `base_url` looks
  production-like, stop and ask for a non-production URL.

Resolve `timeout`:
- Default to frontmatter `timeout` (in milliseconds)
- If missing, default to 30000 (30 seconds)

Resolve `startup_command`:
- Read the `startup_command` frontmatter field if present; store for use
  in Step 2's app-not-running path
- If absent, auto-discovery runs at Step 2 if the app is unreachable

Derive the feature slug from the runbook's `id` frontmatter field by
stripping the `qa-` prefix. Example: `id: qa-user-auth` -> feature slug
`user-auth`.

Note on `auth`: The `auth` field is optional. If present, it contains
hints for authentication setup (e.g., login method and test credentials).
If absent, check the Preconditions section for authentication requirements.
If the app requires login, handle it before executing test cases — either
via precondition steps or by asking the user.

Select execution mode:
- `full` (default): run all test cases
- `rerun-failed`: run only test cases that failed in the most recent results report

### Step 2: Verify App Is Running

Before executing any tests, create the screenshot directory and check
that the base URL is reachable:

```bash
mkdir -p .dark-factory/qa-screenshots/<feature-slug>
agent-browser open <base-url>
agent-browser wait --load networkidle --timeout <timeout>
agent-browser snapshot -i
```

After the snapshot, verify the app is actually working:
1. Check that the page is not blank (snapshot has meaningful content)
2. Check that the snapshot does not contain common error indicators
   (e.g., "502 Bad Gateway", "503 Service Unavailable", "Cannot connect",
   "Application Error", default server error pages)

If the app is not reachable or returns an error page:
1. Run `agent-browser close` to clean up
2. Resolve startup command — in priority order:
   a. `startup_command` from runbook frontmatter (if set)
   b. Auto-discover from repo:
      - Read `package.json` (if it exists): check `scripts` for keys
        `dev:all`, `dev`, `start`, `serve`, `preview` — use first match
        as `npm run <key>` (or `pnpm run <key>` / `yarn <key>` based on
        lockfile present: `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn,
        otherwise npm)
      - If no match in `package.json`, read `Makefile` (if it exists):
        check for targets `dev`, `run`, `serve`, `start` — use first match
        as `make <target>`
   c. If no command found: stop and report "Cannot reach `<base-url>`.
      No startup command found in runbook or repo. Is the application
      running correctly?"
3. Run the resolved command in the background:
   ```bash
   <startup_command> &
   ```
4. Wait 15 seconds, then retry the health check:
   ```bash
   agent-browser open <base-url>
   agent-browser wait --load networkidle --timeout <timeout>
   agent-browser snapshot -i
   ```
5. Re-verify the snapshot (same checks as above — blank page or error indicators).
6. If now reachable: continue to the overlay-handling step.
7. If still unreachable: stop and report "Cannot reach `<base-url>` after
   running `<startup_command>`. The page shows: `<brief description>`.
   Is the application running correctly?"

**Handle overlays:** After verifying the app is reachable, check for overlay
elements that block interaction (cookie consent banners, onboarding modals).
If found, dismiss them before proceeding. For JavaScript dialogs, use
`agent-browser dialog accept` or `agent-browser dialog dismiss`.

### Step 3: Execute Test Cases

**Before starting**: If preconditions require setup (e.g., "user must be
logged in", "test data must exist"), verify or execute them first. If
preconditions include authentication, handle login before test execution.
Report any unmet preconditions to the user.

For each test case (in priority order):

**0. Reset state**: Navigate to `base_url` to establish a known starting
state: `agent-browser open <base_url>` then
`agent-browser wait --load networkidle --timeout <timeout>`.
This ensures each TC starts from a clean page, not from the previous TC's
ending state.

**1. Navigate** to the starting page for the test:
- **URL construction**: Strip trailing slash from `base_url`, ensure path
  starts with `/`, join as `<base_url><path>`. Example:
  `http://localhost:3000` + `/dashboard` = `http://localhost:3000/dashboard`
- If the step contains an explicit path (starts with `/`), construct the
  URL as above: `agent-browser open <base_url><path>`
- If the step says "Open `<page name>`" with no path, navigate via UI
  interactions (click links/menus) rather than guessing a URL
- After every `open`, wait for the page to load:
  `agent-browser wait --load networkidle --timeout <timeout>`

**2. Execute each step** by translating natural language to agent-browser
commands:
- "Open `/path`" or "Navigate to `/path`" -> construct
  `<base_url><path>`, then `agent-browser open <base_url><path>` then wait
- "Open `<page name>`" with no explicit `/path` -> navigate via UI
  interactions (click links/menus). Do not guess or synthesize a URL.
- "Click `'<label>'`" -> `agent-browser snapshot -i` to find the element,
  then `agent-browser click @ref`, then wait then re-snapshot
- "Fill `'<field>'` with `'<value>'`" -> `agent-browser snapshot -i` to
  find the field, then `agent-browser fill @ref "<value>"`, then wait
  briefly if the field may trigger validation/autocomplete/dependent updates
- "Select `'<option>'`" -> `agent-browser snapshot -i` to find the control,
  then `agent-browser select @ref "<option>"`, then wait if it may trigger
  dynamic behavior

**3. Wait strategy**: Use `agent-browser wait --load networkidle --timeout
<timeout>` as the primary wait after interactions. **If `networkidle` times
out** (e.g., the app uses WebSockets, SSE, or polling), fall back to a
brief fixed wait: `agent-browser wait 2000`. Log a warning when the fallback
is used. This prevents mass timeouts on real-time applications.

**4. Re-snapshot** after every interaction that changes the page. Always
wait for the page to settle first (per item 3), then:
`agent-browser snapshot -i`

**5. Run assertions** by inspecting snapshot output. For assertions that
check non-interactive elements (text in divs, banners, paragraphs), use
a full `agent-browser snapshot` (without `-i`) to see all elements, not
just interactive ones.

Assertion translation:
- "VERIFY text `'<text>'` visible in element matching `'<desc>'`" ->
  Locate the element matching `<desc>` in the snapshot. If a `data-testid`
  hint is present, use `agent-browser snapshot -s "[data-testid='...']"` to
  scope. Check that `<text>` appears within that specific element's content.
  Do NOT just search the entire page — the text must be in the specified
  element. If multiple elements match, use the first visible one in DOM
  order and log a warning.
- "VERIFY element matching `'<desc>'` is visible" -> check snapshot for
  an element matching the description
- "VERIFY element matching `'<desc>'` is not visible" -> check snapshot
  confirms the element is absent
- "VERIFY current URL contains `'<path>'`" -> `agent-browser get url`
- "VERIFY field `'<label>'` contains value `'<expected>'`" ->
  `agent-browser snapshot -i` to find the field, then
  `agent-browser get value @ref`
- "VERIFY `<N>` elements matching `'<desc>'` are visible" -> count
  matching elements in snapshot
- "VERIFY element matching `'<desc>'` is disabled" ->
  `agent-browser is enabled @ref` (expect false)
- "VERIFY text `'<text>'` is not visible on page" -> full snapshot,
  confirm text is absent

**6. On step failure within a test case**: If any step fails (element not
found, click fails, assertion fails), mark the entire test case as FAIL.
Record which step failed and why. **Skip remaining steps in this test
case** and move to the next test case. Do NOT attempt subsequent steps
in a failed TC — they will produce cascading, meaningless failures.

**Retry policy for interaction failures (not assertions):** If a `click`,
`fill`, or `select` command fails, wait 2 seconds, re-snapshot, re-locate
the element, and retry once. If the retry also fails, mark the TC as FAIL.
Never retry assertion failures — those indicate real test outcomes.

**7. Record result**:
- All assertions pass -> PASS
- Any step or assertion fails -> FAIL, capture screenshot:
  `agent-browser screenshot .dark-factory/qa-screenshots/<feature-slug>/TC-xxx.png`

**Continue on failure between test cases.** Do not stop at the first
failing test case. Run all test cases and report all results.

### Step 3b: Error Recovery

If any `agent-browser` command returns an error or hangs:
1. Treat it as a step failure — mark the current TC as FAIL with the
   error message
2. Before proceeding to the next TC, verify the browser session is still
   alive: `agent-browser get url`
3. If the session check also fails, attempt recovery:
   - Run `agent-browser close` (may fail, that's ok)
   - Run `agent-browser open <base_url>` to start a new session
   - Run `agent-browser wait --load networkidle --timeout <timeout>`
4. If recovery fails, halt the suite. In the results report, mark all
   remaining TCs as `NOT RUN: browser session lost after TC-xxx`.
5. Proceed to Step 4 to write whatever results were collected.

### Step 4: Produce Results Report

Write immutable results reports in `docs/qa` (create the directory if needed):
- `full` mode: `docs/qa/qa-<feature-slug>-results-<timestamp>.md`
- `rerun-failed` mode: `docs/qa/qa-<feature-slug>-results-rerun-<timestamp>.md`

Also maintain latest pointers:
- `docs/qa/qa-<feature-slug>-results-latest.txt` (single line: path to latest immutable report)
- `docs/qa/qa-<feature-slug>-results-latest.md` (copy of the latest merged suite report)
- After writing the immutable report, update pointers:
  - `printf '%s\n' "<immutable-report-path>" > docs/qa/qa-<feature-slug>-results-latest.txt`
  - `cp "<immutable-report-path>" docs/qa/qa-<feature-slug>-results-latest.md`

**For `full` mode:** Write all test case results.

**For `rerun-failed` mode:** Read the previous report from
`docs/qa/qa-<feature-slug>-results-latest.txt` first. Carry forward
existing results for TCs that were NOT rerun. Replace results only for the
TCs that were re-executed. The final report must include ALL test cases
from the previous latest report, with updated results for the rerun subset.

```markdown
# QA Execution Results: <Feature Name>

**Date:** YYYY-MM-DD
**Runbook:** <path to runbook>
**Mode:** full | rerun-failed
**Results:** X/Y passed

| TC | Name | Priority | Result | Notes |
|----|------|----------|--------|-------|
| TC-001 | <name> | P0 | PASS | |
| TC-002 | <name> | P0 | FAIL | <one-line failure reason> |
| TC-010 | <name> | P1 | NOT RUN | browser session lost after TC-009 |
| ... | ... | ... | ... | ... |

## Failed Test Details

### TC-002: <name>
**Step failed:** Step N — <step description>
**Expected:** <what the assertion expected>
**Actual:** <what was observed>
**Screenshot:** .dark-factory/qa-screenshots/<feature-slug>/TC-002.png
```

### Step 5: Re-run Failed Tests (Optional)

If the user asks to re-run failures after fixes:
1. Read `docs/qa/qa-<feature-slug>-results-latest.txt` to locate the previous
   immutable report
2. If the pointer file does not exist, stop and report:
   "No prior results found for rerun-failed mode."
3. Extract test cases with `Result = FAIL` or `Result = NOT RUN`
4. If none failed, report "No failed tests to rerun."
5. Re-execute only failed/not-run test cases using `rerun-failed` mode
6. Write a new immutable rerun report, then update both latest pointer files

### Step 6: Report Summary

After writing the results file, report:
- "QA execution complete: X/Y tests passed."
- List all failing test cases with one-line reasons
- Path to the immutable report and `results-latest.txt` pointer

### Step 7: Cleanup

Always close the browser session when done, even if tests failed:

```bash
agent-browser close
```

This prevents leaked browser daemon processes. **This step must run at
every exit point** — after Step 6, after Step 2 failure, after Step 3b
session loss, and when execution is interrupted by any error. Before
reporting any terminal error that stops execution, always run
`agent-browser close` first.

## Key Rules

- **Priority order**: Always run P0 tests first
- **Continue on failure**: Run ALL test cases, never stop early (except
  session loss — see Step 3b)
- **Fail fast within a TC**: When a step fails inside a TC, mark it FAIL
  and skip to the next TC
- **Single retry for interactions**: Retry `click`/`fill`/`select` once
  on failure (2s delay + re-snapshot). Never retry assertions.
- **Screenshots on failure only**: Do not screenshot passing tests.
  Screenshots go to `.dark-factory/qa-screenshots/<feature-slug>/TC-xxx.png`
- **Use snapshot -i for interactions, full snapshot for assertions**: Use
  `agent-browser snapshot -i` for finding interactive elements (buttons,
  inputs). Use `agent-browser snapshot` (no -i) when assertions need to
  check non-interactive elements (text, banners, headings).
- **Wait after interactions**: Always wait after clicks, fills, selects,
  and opens that may trigger navigation, AJAX, or dynamic updates.
  Primary: `wait --load networkidle --timeout <timeout>`.
  Fallback on timeout: `wait 2000`.
- **Apply timeout**: Use the frontmatter `timeout` value in all wait commands
- **Scoped assertions**: When an assertion specifies "in element matching
  `'<desc>'`", verify text within that specific element, not the whole page.
  Use `data-testid` scoping via `snapshot -s` when available.
- **Fresh snapshots**: Always re-snapshot after interactions that change
  the page (clicks, form fills, navigations)
- **URL construction**: Strip trailing slash from base_url, ensure path
  starts with `/`, concatenate directly
- **State reset**: Navigate to base_url before each TC to avoid state
  leakage between tests
- **Environment safety**: Never execute QA against production-like URLs
- **Immutable reruns**: Never overwrite prior reports. Write timestamped
  reports and update the latest pointer files
- **Browser cleanup**: Always call `agent-browser close` at every exit
  point (success, failure, or interruption)
- **Error recovery**: On browser crash, attempt session restart. If restart
  fails, mark remaining TCs as NOT RUN and write partial results.
- **No auto-fix**: This skill only reports results. It does not attempt
  to fix failures. The orchestration layer handles fix loops.
